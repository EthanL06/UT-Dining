# apps/mobile

Expo SDK 58 iOS app (Android builds but is not tested). Read the root `AGENTS.md` first. This file says where things are and how data moves, because the code has no comments.

## Data flow

1. Supabase (`utils/supabase.ts`, typed with `@ut-dining/supabase`) is the source of truth. The anon role can read menus from 2 days ago to 3 days ahead (Central time).
2. `hooks/useMenuSync.ts` runs `syncMenuData` in `utils/queries.ts` on launch, on focus and every 30 minutes. `@ut-dining/core` decides whether to sync (`decideSync`) and which menu days to fetch (`planMenuDays`); keep that logic in core, where it has tests.
3. `services/database/sync.ts` writes Supabase rows into a local SQLite cache (Drizzle over expo-sqlite, schema in `services/database/schema.ts`). The small tables are replaced every run; menu days are fetched only when their version changed, one transaction per day.
4. Screens read only the SQLite cache, through TanStack Query hooks in `hooks/` (`useMenuData`, `useFoodData`, `useLocationDetails`). After each cache write the sync invalidates every query except `menuSync`, so screens refresh.
5. Device state lives in Zustand stores in `store/`, persisted to MMKV (`store/rnmmkv-storage.ts`): settings (dark mode and the rest), filters, onboarding, data sync versions, changelog, app launch count, and the meal plan (keyed by Central date, past days read-only). Favorites are in SQLite, keyed by item name plus location name.

The app works offline from the cache. Never make a screen query Supabase directly; add the table to the sync instead.

## Where things are

| Path | What |
|---|---|
| `app/` | Expo Router routes. `(tabs)/` is Home (`index`), Map, Notifications, Settings. `location/[location].tsx` is a dining hall menu, `location_generic/` a place with no menu, `food/[food].tsx` one item, plus `favorites`, `meal-plan`, `changelog` |
| `app/e2e-setup.tsx` | Dev-build-only deep link `ut-dining://e2e-setup` that skips onboarding for Maestro. `?theme=dark` sets the theme, `?serviceStatus=degraded` (or `outage`) fakes the live status so the Home banner shows, `?clock=20:30` (with `&days=3` to move the date, `clock=off` to stop) fixes the app's clock at that Central time on today's Central date (`utils/qaClock.ts`, dev bundle only, kept across relaunches), and `?rating=on` leaves the rating prompt armed |
| `components/` | Shared UI. `components/sheets/` are react-native-actions-sheet sheets registered in `Sheets.tsx` |
| `services/database/` | SQLite cache: `sync.ts` (Supabase to SQLite), `menus.ts`, `locations.ts`, `favorites.ts`, `notifications.ts` (reads and writes), `types.ts`, `schema.ts`. `database.ts` re-exports them all, so existing `~/services/database/database` imports keep working |
| `components/qa/` | Sections of the dev-only QA menu (`app/(tabs)/settings/qa.tsx`) |
| `services/` | Side effects: database, PostHog analytics, push notifications, App Store version check, rating prompt, changelog (read from the Supabase `changelog` table) |
| `utils/` | Helpers. `time.ts` and `date.ts` wrap `@ut-dining/core` for screens; `filter.ts` is the menu filters |
| `drizzle/` | Generated SQLite migrations for the cache. Change `services/database/schema.ts`, then run `npx drizzle-kit generate` here; it also rewrites `drizzle/migrations.js`. Never edit these by hand |
| `e2e/` | Maestro flows, subflows and fixture menus. `e2e/qa/` holds the regression flows `make qa` runs on the sample data. See `e2e/README.md` |

## Conventions

- Styling is NativeWind (Tailwind classes). Dark mode is the in-app Settings switch (`useSettingsStore.isDarkMode`, applied with `Appearance.setColorScheme` in `app/_layout.tsx`), not the system setting. Check every UI change in both themes.
- Every raw string sits inside a `<Text>` (`noReactNativeRawText`), and every label goes through `Text` (and inputs through `TextInput`) from `components/ui/Text.tsx`; Biome blocks importing them from `react-native` anywhere else. Pick a `variant` from the scale (`largeTitle` 34 screen titles, `title1` 28, `title2` 22 sheet and card titles, `title3` 20 section titles and stat values, `headline` 17 semibold, `body` 17, `callout` 16, `subheadline` 15, `footnote` 13, `caption` 12, `caption2` 11, `eyebrow` 12 bold caps, `display` 38 for the day's calorie total) instead of size or `font-*` classes. `emphasized` makes a regular style semibold, `paragraph` adds the relaxed line height for wrapped text, and `tone` (`primary`, `secondary`, `tertiary`, `tint`, `onTint`) or `color` sets the color. Button labels: `subheadline emphasized` up to 44 pt tall, `callout emphasized` at 48 pt, `headline` at 52 pt and up. Font sizes scale with Dynamic Type, so don't set `allowFontScaling={false}`.
- Interactive icons and rows carry a `testID` that Maestro flows use. Keep them when you restyle, and add one when a flow needs to tap something new.
- Release builds merge a touchable's texts into one accessibility label (`"J2 Dining, Closed"`), so Maestro matches names as `'Name(,.*)?'`.
- Imports use the `~/` alias for this folder.
- Icons: import them by name from `lucide-react-native` (`import { Heart } from 'lucide-react-native'`). `babel-plugin-lucide-icons.cjs` rewrites each name to its own `lucide-react-native/icons/<name>` file, so only the icons the app uses get bundled. A namespace import (`import * as Icons`) or a non-icon value export pulls the whole 1.8 MB library back in; the size comment on the PR shows it.
- Images use `Image` from `components/ui/Image.tsx`: expo-image (disk and memory caching, `contentFit` instead of `resizeMode`) wired to NativeWind so `className` works. Biome rejects `Image` and `ImageBackground` from `react-native`. Local assets are `require`d numbers.
- Dates and times are Central, whatever the phone's time zone. Use `@ut-dining/core` (`toCentralTime`, `formatCentral`, `formatCentralDateKey`, `daysBetweenDateKeys`) or `utils/date.ts`, the only file allowed to import `date-fns`. Biome's time zone plugin rejects `Date` getters and setters and `toLocale*String` without a `timeZone` (root `AGENTS.md`).
- Buttons, chips and pills that draw their own background use `PressableScale` from `components/ui/PressableScale.tsx`: a plain `Pressable` (so `className` and `style` work as usual) inside a Reanimated view that presses in to 95% and springs back (`hooks/usePressScale.ts`), and stays still with Reduce Motion on. Layout that sizes the button within its parent (`flex: 1`, `flex: 1.4`) goes in `containerStyle`, because the animated wrapper is what sits in the parent's row. Never pass `className` to a Reanimated or `createAnimatedComponent` view: NativeWind does not style those, so the button loses its size, background and tap area (PR 179). List rows (`GroupedRow`, food rows, meal plan rows), native controls and `GlassButton` keep their own press feedback.
- Haptics go through `utils/haptics.ts` (selection, tap, remove, success, warning, error). Biome rejects a direct `expo-haptics` import anywhere else. Fire `selection` only when a choice actually changes, `success` when an add commits, `remove` when a removal commits, `error` when a refresh or sync fails; plain navigation taps have none.
- Only `services/` (and `utils/supabase.ts` itself) may import Supabase. Biome rejects `~/utils/supabase` and `@supabase/supabase-js` in screens, components, hooks and stores, which keeps the app offline-first.
- Logging goes through `log` in `utils/log.ts`, never `console` (Biome's `noConsole` is an error here). `log.debug` and `log.warn` print only in dev builds; use `warn` for expected failures such as being offline. `log.error` also sends the error to PostHog error tracking in release builds, so keep it for real bugs.
- Errors: `app/_layout.tsx` exports the Expo Router `ErrorBoundary`, which shows `components/AppErrorScreen.tsx` with Try again. A failed SQLite migration shows the same screen with Restart app instead of opening a broken cache. PostHog also captures uncaught exceptions and unhandled rejections (`services/analytics/posthog.ts`).
- State machines are explicit (root `AGENTS.md`). Examples to copy: `hooks/useMultiSelect.ts` (browsing or selecting with ids), `hooks/usePermission.ts` (`checking`, `undetermined`, `granted`, `denied`, refreshed on focus and when the app returns from iOS Settings), `useFoodData` and `useLocationDetails` (`loading`, `ready`, `missing`, `error`, so a screen never spins forever on a missing row), `utils/homeView.ts` and `utils/menuList.ts` (screen states derived from query results, with tests).
- Loading never shows the empty state (root `AGENTS.md`). Use `components/map/SkeletonRows.tsx` style skeleton rows for lists, and give the screen's view function a `loading`/`pending` case, as `utils/mapSheetView.ts` does for the map list and map search.
- Vertical scrolling goes through `components/ui/OverflowScrollView.tsx`, never a plain `ScrollView`: it scrolls and bounces only when the content overflows (`alwaysBounceVertical={false}`), and in sheets, cards and modals it draws a hairline under the pinned header once the content scrolls, so text never hard-clips under an edge. Keep a sheet's title and close button outside the scroll view so they stay put (`components/map/PlaceCard.tsx`). Full screens pass `divider={false}` because the navigation header already handles it; pass `as={ScrollView}` from react-native-actions-sheet inside action sheets. A `FlashList` or `FlatList` gets `alwaysBounceVertical={false}`. Only Home bounces on short content, for pull to refresh. Horizontal chip rows still use `ScrollView`.
- The map sheet (`components/map/MapSheet.tsx`) drags from anywhere on it, like Apple Maps. Scroll views inside it are `SheetScrollView` (`components/map/SheetScrollView.tsx`), which scroll only at the full detent and hand a downward drag to the sheet once their content is at the top. A flick projects with its velocity, so a quick swipe down lowers the sheet.
- Scroll views at the bottom of a tab (the map sheet included) use `contentInsetAdjustmentBehavior="automatic"`, so iOS insets them for the tab bar and its meal strip accessory. Add only a small gap (`SHEET_CONTENT_GAP` in `components/map/PlaceCard.tsx`), never the tab bar or accessory height again, or the content gets a large empty space at the bottom and scrolls when it fits.
- Nearby Menus (opt-in from onboarding's permissions step and Settings > App Permissions) uses iOS region monitoring, never continuous tracking. `components/nearby/NearbyAlertsInitializer.tsx` rebuilds the zones from the SQLite cache after each sync and registers them with `Location.startGeofencingAsync`; `services/nearby/nearbyAlerts.ts` defines the background task, stores the zones and the sent log in the `nearby-alerts` MMKV instance (the task cannot read React state), and posts a local notification with `redirect_url` (that type is not saved to the Notifications inbox). The rules are pure and tested in `utils/nearbyAlerts.ts`: only `Dining Hall` locations with menus, halls within 75 m share one zone (J2 and JCL are both in Jester, so one notification names whichever are open and links to the `/nearby` picker when both are), at most 20 zones (the iOS limit), and only while a hall is open with a menu. Because Jester and Kinsolving are dorms, it only notifies on a real arrival (`recordEnter`/`recordExit`, which need exit events too): at most once per zone per day, only after 2 hours outside the zone, never for a zone the phone stayed in overnight (treated as home for 14 days), and never for a zone muted with the notification's "Stop for This Hall" action (Settings > Nearby Menus turns them back on). Whenever monitoring starts (turning it on, a cold launch, changed regions), expo-location asks iOS for each region's current state and delivers it as a synthetic Enter or Exit, so only real transitions count: an Enter while already inside or an Exit while already outside changes nothing, and the first event per zone within `BASELINE_MS` of `startGeofencingAsync` only records where the phone is (`startBaseline`). The history lives in the same MMKV instance. It needs Always location, asked only after the person turns it on. QA Menu > Nearby Menus fires a zone's notification without walking there (skipping the arrival rules and the daily limit); in the Simulator, Features > Location > Custom Location triggers a real entry.
- At label zoom the map stacks pins that would overlap (`stackOverlappingPins` in `utils/mapPlaces.ts`) into a column 40 pt apart, so every place in Jester stays tappable.
- The App Store rating prompt never fires on launch. `ratingService.requestAfterHappyMoment(trigger)` (`services/rating/rating.ts`) asks 1.5 s after a happy moment: adding a favorite once there are 5 or more (`utils/foodActions.ts`), or opening a menu that has a favorite, or for people who never favorite, opening any menu after 10 launches over 7 days (`hooks/useRatingPromptOnMenuView.ts`, `menuViewTrigger`). `decideRatingPrompt` in `utils/ratingPrompt.ts` (tested) needs 3 launches over 3 days, finished onboarding and a connection, and allows one prompt per app version with at least 120 days between prompts. Each request is captured in PostHog as `rating_prompt_requested`. The QA Menu's Prompts section shows and resets it.
- Pure helpers that do not import React Native, Expo or MMKV get a Vitest test next to them (`utils/*.test.ts`); `pnpm --filter @ut-dining/mobile test` runs them in about 1 s with `TZ=America/Chicago`.

## Dev app, PR previews and OTA updates

- `APP_VARIANT` picks the app. Unset (the `production` EAS profile) is the App Store app: bundle `com.ethanl06.ut-dining`, channel `production`, runtime version `appVersion`, prod Supabase. `development` and `preview` are both **UT Dining (Dev)**: bundle `com.ethanl06.ut-dining.dev`, dev Supabase (EAS environments `development` and `preview`), runtime version `fingerprint`, channel `staging`.
- Dev and App Store builds can never share an update: different bundle, different channel, and a fingerprint runtime never equals an `appVersion` one. `scripts/ci/mobile-preview.sh` also refuses the `production` channel and checks the resolved bundle and runtime policy before it publishes.
- OTA updates are on in the dev app only when `DEV_UPDATES=1`: the `preview` profile sets it in `eas.json` (so `eas build` and the EAS worker agree), `scripts/ci/mobile-preview.sh` exports it for `eas update`, and a local device build opts in with it. Local, simulator, E2E and screenshot builds leave it unset, so a test never runs JS downloaded from staging instead of the code under test. The value is part of the fingerprint, so a build and its updates must agree on it; EAS fails the build with "Runtime version mismatch" otherwise.
- `fingerprint.config.cjs` is the default `balanced` preset plus `ExpoConfigExtraSection`, because `extra.gitCommit` changes on every commit. Without it every commit would need a new build.
- `.github/workflows/mobile-preview.yml` runs `scripts/ci/mobile-preview.sh` (`make mobile-preview ARGS="pr <n>"` locally, needs `EXPO_TOKEN`):
  - Push to `staging`: publishes to channel `staging`, so the installed dev app picks the change up on its next launch.
  - A PR: publishes to channel `pr-<n>` and posts one PR comment with the links and a QR code for `ut-dining-dev://preview/<n>` (`app/preview/[pr].tsx`). The dev app also registers the `ut-dining-dev` scheme, because the App Store app owns `ut-dining`. Switching channels goes through `services/qa/updates.ts` (`Updates.setUpdateRequestHeadersOverride`); QA Menu > Back to Staging switches back.
  - `scripts/ci/preview-index.sh` keeps the list the QA menu's PR Previews section shows: `previews.json` and `qr/pr-<n>.png` in the public `qa-previews` bucket of **dev** Supabase (it refuses prod). Each entry has the PR title, commit, fingerprint and build link, so the app greys out previews that need a newer build. Each PR writes its own `entries/pr-<n>.json`, and `previews.json` is rebuilt from those files and read back until it matches them, so preview jobs that run at the same time never drop each other's entries. Closing a PR removes its entry. Nothing in it is secret: it is PR titles from a public repo.
  - Either way, when no `preview` build exists for the iOS fingerprint (native code changed), it starts one on EAS with `--no-wait` and links its install page. PRs opened by bots never start builds. The free plan has 15 iOS builds a month.
- A change to native dependencies, config plugins or native parts of `app.config.js` changes the fingerprint and needs a new build installed before its OTA updates apply.

## Verifying

- Static: `make verify` from the repo root.
- On a Simulator (macOS only): the verifier-mobile skill, or `make e2e SIM=<UDID>` for the Maestro suite.
- A release simulator app: `make ios-app`. It runs a full Xcode build only when the lockfile, a `package.json`, `app.config.js`, the app icons or the Xcode version change; otherwise it reuses the saved native build and rebuilds only the JavaScript in a few minutes. `scripts/qa/ios-sim-app.sh --key` prints the native key, and `--swap <app>` rebuilds the JavaScript of an existing release app.
- A change to native dependencies, `app.config.js` or `eas.json` needs a new development build before anything can be verified.
- The Expo dev client's floating Tools button covers the food screen's top-right icons in dev builds. Turn it off in the dev menu before tapping there; release builds do not have it.
