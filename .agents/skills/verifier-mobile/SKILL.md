# verifier-mobile

## Setup

1. macOS with Xcode. On Linux, or with no Xcode, this verifier is BLOCKED; say so and ask for a run on Ethan's Mac.
2. Data: start local Supabase with verifier-data setup steps 1 to 5, including its port check, then `node scripts/env.ts --local`. It writes `apps/mobile/.env.local` with the local `EXPO_PUBLIC_SUPABASE_URL` from `supabase status`, which the Simulator reaches on the Mac's localhost. Load several days of menus, because the hosted projects hold up to five days and one day hides row-limit bugs: run the scraper (verifier-data step 5) with `DAYS_TO_SCRAPE=5`. Local Supabase allows 3000 rows per response (`max_rows` in `supabase/config.toml`) but the hosted projects allow 1000, so for any change to the sync or to queries, set `max_rows = 1000` for the run before `supabase start` (restore it at teardown, never commit it). Never point the app at production or the hosted dev project.
3. Pick one simulator and use its UDID in every command, never `booted`: more than one simulator may be booted, and each worktree should own its own. List them with `xcrun simctl list devices available`, choose one, `export SIM=<UDID>`, then `xcrun simctl boot "$SIM"` (an "already booted" error is fine) and `open -a Simulator`.
4. Check that the simulator has a development client, not just the bundle id. `APP="$(xcrun simctl get_app_container "$SIM" com.ethanl06.ut-dining.dev)"` must succeed, and `ls "$APP" | grep -q EXDevLauncher.bundle` must be true. A build that has `main.jsbundle` and no `EXDevLauncher.bundle` is a release build: it ignores Metro and carries its own Supabase URL, so it would test the wrong code and data. When the check fails, or the change touches native code, `app.config.js` or a native dependency, build and install a dev client: `pnpm --filter @ut-dining/mobile ios --device "$SIM" > "$run/build.log" 2>&1` (several minutes). For a JS-only change the installed dev client is enough.
5. Start Metro for the worktree: `pnpm --filter @ut-dining/mobile start --port 8081 > "$run/metro.log" 2>&1 &`. `$!` is the pnpm wrapper, not the server, so do not rely on it for teardown. Wait for `curl -sf http://localhost:8081/status` to answer `packager-status:running` (about 6 s). Note the time; the device log check starts from it.
6. Open the app: `xcrun simctl launch "$SIM" com.ethanl06.ut-dining.dev`. It usually reconnects to Metro on 8081 by itself. If the dev client shows its launcher instead, open `xcrun simctl openurl "$SIM" "exp+ut-dining://expo-development-client/?url=http%3A%2F%2Flocalhost%3A8081"`. The first bundle takes about 15 s. On a fresh install, finish onboarding once.
7. Dismiss the baseline noise on every cold start before you tap anything: the alert "Must use physical device for push notifications" (OK), and, when `EXPO_PUBLIC_POSTHOG_API_KEY` is empty, the LogBox toast `usePostHog was called without a PostHog client` over the tab bar (its X). Both are known and are not a FAIL.
8. Sync the local data. The app keeps a SQLite cache and only syncs every few hours, so it can still show old data from another backend. Open Settings, tap Sync Data, and wait for `Successfully synced` in `$run/metro.log`. Pull-to-refresh is not a reliable trigger. Relaunch the app after the sync, because some Home status text only updates on launch.

## Steps

1. For each screen the claim names, open it with a deep link on the `ut-dining` scheme: `xcrun simctl openurl "$SIM" "ut-dining://<path>"`. Routes: `ut-dining://` (home), `/map`, `/notifications`, `/settings`, `/favorites`, `/meal-plan`, `/location/<location name, URL-encoded>` for dining halls (for example `/location/J2%20Dining`), `/location_generic/<name>` for other places. The food screen needs more than a name (`food`, `menu`, `category` and `location` params), so reach it by tapping an item on a location's menu. Deep links stack screens on top of each other, so relaunch the app (`xcrun simctl terminate "$SIM" com.ethanl06.ut-dining.dev`, then launch) between screens when a clean stack matters.
2. Screenshot each state: `xcrun simctl io "$SIM" screenshot "$run/<claim>-<state>.png"`. Dark mode is the in-app Settings > Dark Mode switch, not the simulator appearance: `xcrun simctl ui "$SIM" appearance dark` does not change the app theme. Check both themes with the simulator appearance set to light, and check that the native tab bar follows the in-app switch. Look at each screenshot to confirm the theme really changed before you call it dark.
3. Taps: use the iOS Simulator tool of the agent when it has one (tap, drag, type). A short tap does not flip the Dark Mode switch; a horizontal drag across it does. With no tool that can tap, mark the tap part BLOCKED and say so.
4. Sync completeness, after setup step 8: the app's cache must hold every row the anon role can read. Read the cache with `sqlite3 "$(xcrun simctl get_app_container "$SIM" com.ethanl06.ut-dining.dev data)/Documents/SQLite/database.db" "select (select count(*) from menu),(select count(*) from menu_category),(select count(*) from food_item)"`, and compare it with the server, counting only menus in the anon read window: `psql_local -c "select count(*) from food_item f join menu_category c on c.id = f.menu_category_id join menu m on m.id = c.menu_id where m.date between (timezone('America/Chicago', now()))::date - 2 and (timezone('America/Chicago', now()))::date + 3"`. A `food_item` count of exactly 1000, or any count below the server's, is a FAIL. So is a menu category with no items in the app when it has items on the server.
5. Logs, for red screens, errors and crashes made during the run. Metro: `$run/metro.log`. Device: find the executable with `xcrun simctl listapps "$SIM" | grep -A12 com.ethanl06.ut-dining.dev | grep CFBundleExecutable`, then `xcrun simctl spawn "$SIM" log show --start "<Metro start time, YYYY-MM-DD HH:MM:SS>" --predicate 'process == "<executable>"' > "$run/device.log"` and `grep -nE 'RCTFatal|fatal error|Terminating app|Unhandled JS Exception' "$run/device.log"`. The rest of that log is mostly UIKit noise. A red screen, a LogBox error other than the baseline in setup step 7, or a crash from this change is a FAIL.

## Teardown

Stop the Metro server you started: `kill $(lsof -tiTCP:8081 -sTCP:LISTEN)`. Killing the pnpm PID leaves the Expo `node` child listening. Then do the verifier-data teardown if you started Supabase. Set the in-app theme back to what it was. Leave the simulator and the app as you found them, booted or shut down. The app's cache keeps this run's local data, so tap Sync Data again before using the simulator against another backend.

## Result

PASS, FAIL or BLOCKED for each claim, with screenshots and log paths. Say which simulator and which build (dev client date) you used.

## Track record

- 2026-11-04, staging b8aa5f6, iPhone 17 (iOS 26.5), dev client built 2026-10-25: home, J2 Dining, map, settings, favorites and meal plan PASS in light and dark. This run found the port, release build, stale cache, dark mode and Metro teardown problems that the steps above now cover.
