# Working from a cloud session

Claude Code cloud sessions run in a Linux container behind a proxy. These limits cost real time before they were written down.

## GitHub

- Write with Ethan's token: `gh api` REST calls use `GH_TOKEN` from the environment. `gh pr` and `gh issue` fail because the proxy blocks GraphQL, so open a PR with `gh api repos/EthanL06/UT-Dining/pulls -X POST -f base=staging -f head=<branch> -f title=... -f body=...`. The GitHub MCP tools work for reads, but writes made with them show "with Claude" on GitHub, so do not use them for writes.
- The proxy appends a "Generated by Claude Code" footer to every PR body and comment. It cannot be removed from a session; leave it.
- Blocked by the proxy: ruleset writes (`/rulesets` returns 403) and branch deletes (`git push --delete` and `DELETE git/refs`). For a ruleset, put the JSON in the PR or a project file and ask Ethan to apply it. For a branch you must delete, push a commit to it with a push-triggered workflow that deletes its own ref with `GITHUB_TOKEN` (`contents: write`), then delete that run. Usually just leave the branch.
- Force pushes are refused by the session's safety check. To update a PR branch, merge `staging` into it; PRs are squash merged, so the history does not matter.
- `Fixes #N` does not close issues when a PR merges into `staging`, because it is not the default branch. Close them by hand with `state_reason=completed`.
- CI (`ci.yml`) takes about a minute. The Maestro iOS workflow runs only on PRs from `staging` into `main` and on manual dispatch.

## Screenshots for a PR

Screenshots go on an orphan branch, never on the PR branch:

```sh
git switch --orphan assets/<topic>
git rm -rq --cached . 2>/dev/null || true
mkdir -p apps/dashboard apps/website
printf '{ "git": { "deploymentEnabled": false } }\n' | tee apps/dashboard/vercel.json > apps/website/vercel.json
cp /path/to/*.png .
git add apps/dashboard/vercel.json apps/website/vercel.json *.png
git commit -m "chore: screenshots for <topic>"
git push -u origin assets/<topic>
```

Embed them in the PR body as `https://raw.githubusercontent.com/EthanL06/UT-Dining/assets/<topic>/<file>.png`. Without both `vercel.json` files, Vercel tries to build the branch, fails, and emails Ethan.

The container has no iOS Simulator. Screenshots of the iOS app come from Ethan's Mac through a Remote Control session, and the Mac's local permissions refuse to send image files out of it or to `git push`. Web screenshots work in the container: agent-browser with `AGENT_BROWSER_EXECUTABLE_PATH=/opt/pw-browsers/chromium AGENT_BROWSER_ARGS=--no-sandbox`.

## Which Supabase

| Project | Used by | Rule |
|---|---|---|
| Local (Docker) | Every verifier, tests, `make dev` | The default. `make db-up` starts `dockerd` itself when the session runs as root |
| Hosted dev (`ut-dining-dev`) | Cloud sessions when `SUPABASE_DEV_*` vars are set (the SessionStart hook runs `scripts/env.ts --dev`), Vercel previews, `scraper-dev.yml` | Read only from a session. Never write to it from a build or a verifier |
| Production | The shipped app, Vercel production, the daily scraper on `main` | Never. `scripts/env.ts` refuses its ref and `make doctor` fails on it |

`make doctor` prints which project each app's `.env.local` points at. After the SessionStart hook, run `make env-local` before any verifier so the apps use local Supabase.

## Generated database types

`packages/supabase/src/database.types.ts` is generated from the migrations, so two PRs that each add a migration both rewrite it and conflict. Do not merge the file by hand:

1. Resolve the conflict by taking either side (`git checkout --theirs packages/supabase/src/database.types.ts`).
2. `make db-up && make db-reset` so the local schema has every migration from both sides.
3. `make db-types`, check that the diff only adds what the migrations explain, and commit.

Migration file names start with a timestamp and run in that order. When `staging` gained a migration with a later timestamp than yours, and yours depends on it, rename yours with `make db-new` and move the SQL, before the PR merges. A migration already on `staging` is never edited or renamed.
